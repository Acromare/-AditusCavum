# AditusCavum v0.2.1

## Added: injectable interface clients

This release adds a third integration style alongside service inheritance and direct assistant injection. Consumers can declare an interface and let the framework implement the predefined chat operations at runtime:

```java
import com.heng.aditus.AditusOperations;
import com.heng.aditus.annotation.AditusClient;

@AditusClient
public interface ExamAI extends AditusOperations {
}
```

Inject `ExamAI` into a controller or service and call `examAI.chat(...)`, `examAI.stream(...)`, or `examAI.clearConversation(...)`. The user does not write an implementation class, forwarding methods, or `super` calls.

### New public API and configuration

- `AditusOperations`: defines both chat overloads, both streaming overloads, and conversation cleanup with their existing argument and return types.
- `@AditusClient`: marks a public, non-sealed interface extending `AditusOperations` for registration.
- `aditus-cavum.client.base-packages`: optional comma-separated scan packages, replacing the default Spring Boot auto-configuration packages.
- Java `default` methods on clients are supported for explicitly implemented convenience behavior. Unknown abstract methods are rejected at startup.

## Changed: shared contract and startup registration

- `AditusAssistant` and `AditusService` now implement `AditusOperations`; their existing public operations and execution behavior remain available.
- `AditusConfiguration` registers a static client scanner before normal bean creation. Annotated interfaces inside the configured packages are discovered and validated at startup.
- Each client is registered through a `FactoryBean` exposing its interface type and a singleton JDK dynamic proxy. Bean names use the fully qualified interface name, avoiding simple-name collisions across packages. Repeated scanning of the same client does not create duplicate beans.
- Assistant resolution occurs only when an operation is called, so proxy discovery and object methods do not initialize or call a provider. Reflection wrappers are unwrapped to preserve the original application/model exception.

This is delegation to the existing assistant, not another model engine. There are no new runtime dependencies, HTTP endpoints, generated source files, automatic retries, or new tool-execution rules.

## Before and after

The v0.2.0 inheritance style remains supported:

```java
@Service
public class ExamAI extends AditusService {
}
```

For services that only expose the framework's operations, v0.2.1 also supports:

```java
@AditusClient
public interface ExamAI extends AditusOperations {
}
```

Update imports and replace class inheritance with the interface declaration. Remove `@Service` and any constructor that existed only to inject the assistant. Keep existing HTTP routes and invoke the client from the controller. Preserve business logic when migrating; a proxy does not automatically reproduce custom overrides.

## Upgrade

```xml
<dependency>
    <groupId>com.github.Acromare</groupId>
    <artifactId>-AditusCavum</artifactId>
    <version>v0.2.1</version>
</dependency>
```

The repository remains `https://jitpack.io`. Place the interface under the application's Boot base package or configure `aditus-cavum.client.base-packages`. Inject the specific client interface rather than the common `AditusOperations` type when multiple implementations exist.

The [interface-client guide](https://github.com/Acromare/-AditusCavum/blob/v0.2.1/docs/clients.md) includes complete imports, HTTP integration, package scanning, custom default methods, startup validation, and migration details.

## Scope and limitations

- This proxy implements the predefined operations. Arbitrary abstract methods such as `answerAnything(...)` have no automatic model mapping and cause a startup error.
- All clients share the existing assistant, model configuration, and conversation store. Two interfaces using the same conversation ID share history; the interface name is not an isolation boundary.
- Streaming still returns lazy `Flux<String>` deltas. Its completion, cancellation, memory, and tool-side-effect behavior is unchanged.
- Tool definitions still use `@MarkTheRuins` and `@Need`. An `@AditusClient` interface does not automatically define model-callable tools.
- Direct injection and `extends AditusService` remain supported. Java 17+ and the Spring Boot 4.1.1 dependency baseline are unchanged.

## Verification

Seven new tests cover Boot package scanning, constructor injection, singleton identity, all inherited operations, default methods, streaming laziness, system prompts and history, isolation and cleanup, overlapping scan packages, unannotated interfaces, original error propagation, and startup rejection of unsupported declarations. Default-model startup is tested without a provider key to check that creating a proxy does not make a provider call or introduce a circular dependency.

The complete suite has 24 passing tests, including the existing inheritance, configuration, tool, memory, and streaming regressions.

The consumer application starts with constructor injection of the annotated interface. A live provider call during this release check encountered a TLS handshake failure while routed through a VPN; no successful live-provider response is claimed for this release. Automated proxy behavior tests use a local model implementation, and the existing streaming tests use a local HTTP server.
