# AditusCavum v0.1.8

## Fixed: consumer YAML configuration was overridden

AditusCavum v0.1.7 packaged an application-level `application.properties` in its dependency JAR. Spring Boot gives properties files precedence over YAML at the same configuration location. As a result, the library's settings could override the consuming application's `application.yml`.

For example, a consumer configured a Qwen endpoint, API key, and model in YAML, but the library supplied:

```properties
spring.application.name=AditusCavum
aditus-cavum.model.base-url=${ADITUS_MODEL_BASE_URL:https://api.openai.com/v1}
aditus-cavum.model.api-key=${ADITUS_MODEL_API_KEY:}
aditus-cavum.model.model=${ADITUS_MODEL_NAME:gpt-4o-mini}
```

With `ADITUS_MODEL_API_KEY` unset, the bound API key became empty. The client threw `Set aditus-cavum.model.api-key before calling the model` before sending any HTTP request. The application name, endpoint, model, and chat settings could also be overridden.

## Implementation

- Removed `src/main/resources/application.properties` from the library. The published JAR no longer contributes application-level configuration.
- Kept default values in `AditusProperties`: the OpenAI-compatible base URL, `gpt-4o-mini`, five tool rounds, twenty memory messages, and an empty system prompt. The API key must come from consumer configuration.
- Preserved `@AutoConfiguration`, `@EnableConfigurationProperties(AditusProperties.class)`, and the `AutoConfiguration.imports` entry. No manual bean registration or Java API changes are required.
- Added `src/test/resources/application.yml` as a consumer configuration fixture with a dummy key. This test-only resource is excluded from the production JAR.
- Extended the configuration regression test to check the application name, base URL, API key, model, maximum tool rounds, memory limit, and system prompt.

## Validation

- Restoring the old properties resource in the compiled classpath reproduced the failure: `expected: <consumer-application> but was: <AditusCavum>`.
- After `mvn clean verify`, all four tests passed, with zero failures or errors. The clean build removes stale resources left by earlier builds.
- Inspected the resulting JAR for absence of application configuration files and presence of the auto-configuration registration.
- A configuration probe using the consumer's YAML reproduced an empty key with the v0.1.7 JAR and a populated key with the corrected framework. No real key was printed and no provider request was needed for this check.

## Upgrade

Use the JitPack repository and update the dependency:

```xml
<repository>
    <id>jitpack.io</id>
    <url>https://jitpack.io</url>
</repository>
```

```xml
<dependency>
    <groupId>com.github.Acromare</groupId>
    <artifactId>-AditusCavum</artifactId>
    <version>v0.1.8</version>
</dependency>
```

Rebuild and restart the consuming application. When building the framework from source, run `./mvnw clean verify` (Windows: `./mvnw.cmd clean verify`).

### Environment variable migration

The removed resource also provided custom environment-variable aliases. If you relied on these aliases, declare their mapping in your own configuration:

```yaml
aditus-cavum:
  model:
    base-url: ${ADITUS_MODEL_BASE_URL:https://api.openai.com/v1}
    api-key: ${ADITUS_MODEL_API_KEY}
    model: ${ADITUS_MODEL_NAME:gpt-4o-mini}
  chat:
    max-tool-rounds: ${ADITUS_MAX_TOOL_ROUNDS:5}
    max-memory-messages: ${ADITUS_MAX_MEMORY_MESSAGES:20}
    system-prompt: ${ADITUS_SYSTEM_PROMPT:}
```

Set `ADITUS_MODEL_API_KEY` in the runtime environment or IDE run configuration. Existing explicit `aditus-cavum.*` YAML/properties values continue to work. The framework no longer injects the legacy aliases or its own application name.

## Compatibility

- Java 17 or newer; Spring Boot dependency baseline remains 4.1.1.
- No public Java API changes or new runtime dependencies.
- This release fixes configuration ownership only; model transport, tool execution, and conversation-memory behavior are unchanged.
