# AditusCavum v0.2.0

## Inherit the service, override only what you need

Applications previously repeated assistant injection and forwarding methods in each chat service. This release adds the optional `AditusService` base class so an application service can be just:

```java
import com.heng.aditus.AditusService;
import org.springframework.stereotype.Service;

@Service
public class AIService extends AditusService {
}
```

The service inherits `chat(message)`, `chat(conversationId, message)`, `stream(message)`, `stream(conversationId, message)`, and `clearConversation(conversationId)`. Existing controllers can keep calling the application service without any changes.

## Implementation details

- Added one abstract base class in `com.heng.aditus`. It holds the Spring-injected `AditusAssistant` and delegates operations to the existing implementation.
- The base class has no component annotation and is not automatically instantiated. Register your concrete subclass with `@Service` or `@Bean`. Spring processes the inherited injection point; no subclass constructor or injection field is needed.
- Public operations remain overridable. Call `super.chat(...)` or `super.stream(...)` to reuse the framework behavior from an override.
- Single-argument convenience methods delegate to their two-argument counterpart using a null conversation ID, ensuring a two-argument override also applies to stateless calls.
- Chat and streaming overrides are independent. Implement a rule in both if it must govern both operations; use lazy Reactor operators for streaming customization.
- The existing assistant, model transport, configuration binding, tool execution, memory semantics, and streaming lifecycle are reused without introducing another engine or new dependencies.

## Upgrade

```xml
<dependency>
    <groupId>com.github.Acromare</groupId>
    <artifactId>-AditusCavum</artifactId>
    <version>v0.2.0</version>
</dependency>
```

To simplify an existing forwarding service, extend `AditusService` and remove the redundant assistant field, forwarding methods, and `@RequiredArgsConstructor` if no other fields need it. Keep the subclass's `@Service` annotation and your controller's HTTP mappings.

Only remove methods that are pure forwarding; preserve business logic as overrides. If your service already extends another class, continue injecting `AditusAssistant` directly. Plain Java consumers can still construct `AditusAssistant` explicitly; the new base service requires Spring-managed injection.

## Validation and compatibility

Seventeen automated tests pass. Three new Spring application-context tests verify inherited injection and operations, lazy streaming, system prompts and history, conversation isolation and cleanup, override dispatch through convenience methods, and continued direct assistant use without any base-service bean. The existing fourteen configuration, tool, memory, and streaming tests remain in place.

The desktop consumer service has been reduced to an empty subclass and is validated with its existing controller. No public methods have been removed. Java 17+, Spring Boot 4.1.1, and the runtime dependencies remain unchanged. In-memory conversations are still local to one process; services using the same conversation ID share that assistant's memory. Serialize active turns for each conversation.
